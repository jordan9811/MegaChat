# Later the same day

*Appended after the sections above; nothing earlier was edited.*

## What happened
- **The spend protection is now live and proven with real traffic.** I put a real
  participant into the production video service for about fifteen seconds and
  watched the whole round trip: the service told us they arrived, told us they
  left, the session opened and closed cleanly, nothing was left hanging, and the
  recorded length matched the stopwatch. Most importantly the spending meter is
  now reading a **real number instead of zero** — that was the entire point of
  turning this on. Cost of the test: 0.23 minutes against a 10-minute budget.
- **Found a bug in the safety check itself.** I was asked to explain any gap
  between the service's numbers and ours, and the gap turned out to be the
  comparison, not the data. Our own records survive a restart; the service's
  records start from scratch every time we deploy. Comparing the two was
  comparing a full day against a few minutes, so it screamed "mismatch" after
  *every single deploy* with nothing actually wrong. A monitor that cries wolf
  after every deploy is worse than no monitor, because you learn to ignore it.
  It now only compares periods both sides actually saw, and says "not enough
  data yet" instead of guessing. (Issue L8.)
- **Clips that are too short to verify can no longer be sold.** This closes the
  item you were asked to decide on: there is now a minimum clip length. The
  number isn't invented — it's *taken from* the length the verifier needs to
  read a code off a stream, so if that requirement ever changes the minimum
  follows it automatically instead of drifting apart. A short clip is refused
  while recording, before any wallet prompt, and refused again on the server
  **before the payment step**, so nobody is ever charged for one. Rooms can't
  set themselves below it.
  - You asked what happens to short clips already in the system. **There are
    none, and there can't be** — clips only exist in memory between being paid
    for and being played, and are deleted afterwards. Nothing to clean up.
- **Refunds are now one road instead of several paths.** Money can go back for
  four named reasons — unverifiable clip, handle never claimed, dispute, manual
  operator action — and a reason that isn't on the list is refused outright. The
  important part: a contribution can only be refunded **once**, no matter how
  many reasons arrive for it, so a dispute landing on a clip that already
  refunded doesn't pay it twice. Every refund records why, who did it, and what
  it relates to. Still no real money moving.
- **Two things you reported mid-day, both fixed and deployed**: your Twitch
  account is now used by default instead of being buried in advanced settings,
  and the OBS overlay going black while viewers saw the stream fine. That second
  one was ours — two overlays open anywhere were kicking each other off.

## Problems and how we handled them
- The reconciliation gap could easily have been written off as "close enough" or
  reported as a scary number with no explanation. It was neither; it was a real
  defect in the thing meant to catch defects.
- One of my own automated checks was still asserting the *old* overlay behaviour
  from before this morning's black-screen fix, so it failed. That's the check
  doing its job — I updated it to assert the new rule rather than the old one.
- A test room I set up looked like the minimum-length rule was broken when it was
  really my test room being priced when I meant it to be free. Worth naming
  because the error message pointed at the wrong thing entirely.

## Outstanding
- **You: confirm the hosting service isn't set to sleep when idle.** Unchanged
  from this morning, still the only thing I can't check myself.
- **The biggest remaining hole in the money model: there is no way to reverse a
  payout.** Refunds can only return money still being held. Once it's released
  to a streamer, nothing in the system can pull it back — a dispute decided
  against someone after they've been paid has no mechanism. It needs its own
  design, not another reason code. Written up in `OPEN-ISSUES.md`.
- **New for later: record how many people were watching at each clip play.**
  Payouts should scale with audience — a clip played to forty people shouldn't
  be worth the same as one played to forty thousand, and neither should be worth
  nothing. This has to be built *at the same time* as the real stream checking,
  because viewer counts can't be looked up after the fact. Any play recorded
  before then can never be priced this way. (Issue B6.)

## Outlook: bullish, unchanged
- Spend protection moved from "built but inert" this morning to **live, tested
  with real traffic, and reading real numbers**. That was the main caveat on
  this morning's bullish call and it's now closed.
- Two more real defects found by looking rather than waiting — the false-alarm
  monitor and the black OBS overlay — both in things that were assumed fine.
- What still keeps it from being unreserved: no real funds have ever moved, and
  the no-clawback gap above is a genuine design hole rather than a task.
