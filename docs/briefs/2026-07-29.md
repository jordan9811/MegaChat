**It took the broadcast about ninety seconds to disprove two things every green

### P0-1: the handle was never passed to the frame sources

`verifyAirSession` read `session.handle`. Air sessions carry a `claimId`, not a
handle — the handle lives on the reserved handle the claim points at. So it was
`undefined` for every session ever created, and the real frame sources built
`https://www.twitch.tv/` with nothing after the slash. yt-dlp rejected it as an
unsupported URL.

**Live grabs and VOD discovery were both dead on arrival, for everyone.** On the
VOD path it surfaced as a 500 rather than the graceful `SOURCE_UNAVAILABLE` the
design promises. No gate could catch it, because every gate drives the verifier
with fixtures and fixtures never touch that argument.

### P0-2: the media timeline is not our clock

Measured, not guessed:

| path | measurement |
|---|---|
| VOD | frame requested for wall-clock T showed the badge from **T−16.7s** and **T−15.0s** on two independent samples |
| live HLS | same badge appeared **~12-25s** behind the encoder |
| `created_at` vs stream start | only 5s — it explains a third of the VOD error; ingest/transcode is the rest |

Codes rotate every **4 seconds**. Both paths were therefore sampling roughly
four rotations off: every clip read a perfectly legible 28px badge and verified
nothing. The documented "±1.5s tolerance" assumed an alignment that does not
exist in practice.

Fixed by shifting the VOD seek by the measured constant and widening the
accepted-code window. The clip-binding safety property is untouched — the window
is still built only from *that* clip's codes, so widening it can never let one
clip's code satisfy another, and the gate asserts exactly that.

**The honest limits, asserted in the gate rather than buried:** the seek constant
comes from ONE VOD. A 4s residual still verifies but collapses confidence to
AMBIGUOUS — a streamer who did the work, sent to human review. A residual past
the clip's own code coverage cannot verify at all, and no wider filter fixes it.
Per-VOD calibration is the right answer, is filed, and is not built; decoding a
frame against all of a session's codes to derive the true offset already works,
because that is how the 16.7s figure was measured.

## What the corpus was actually measuring

The entire synthetic corpus was generated from a single issued code,
`97-TXFV`. So "1080p 100%, 720p 100%, 480p 92%" described one glyph sequence,
not the alphabet. Meanwhile the end-to-end pipeline gate, which issues a fresh
random code every run, had been passing and failing intermittently against the
same 720p encode. Both could not be true.

Swept across distinct issued codes through the shipped path — real overlay
page, real 720p/3Mbps re-encode, real decoder — detection was **55-75%, with
4 to 9 of every 20 codes never read at all**. Deterministic, not noisy: every
code read on all its frames or none of them. At 720p. The documented minimum
verifiable quality. That is this project's own worst failure mode — the
streamer does the work and quietly is not paid — sitting in the pipeline the
whole time, invisible because the corpus asked the same question once.

Two defects, both un-catchable by a fixed-sample corpus:

1. The decoder's alignment window was a flat ±2px, tuned against that one
   code. Its own comment recorded the optimum sitting at `dx=+2` — on the
   boundary of the window that had been chosen. A search whose answer lands on
   its own edge is usually too small for the cases not yet tried. The true
   decode optimum sits up to ~3 dots from the ring-contrast peak; every
   recovered miss landed at dx=-6 or -7 at 720p, and none beyond, even
   searching ±16. All misses decoded as `"-------"`, the border-row artifact
   the selection logic already warned about.
2. `locateRing` returned only the highest ring-*contrast* hypothesis, which is
   not the same as the right one — it sometimes crowned a pitch-0.75 patch of
   background over the true pitch-2.5 matrix, and no jitter around that winner
   could reach the real matrix.

Fixed: the window is expressed in **dots** and converted at the measured
pitch, so it holds at any resolution instead of the one it was tuned on; the
locator returns ranked candidates and the matched filter tries the top 3. Cost
is controlled by scanning wide, stopping at the first alignment that reads the
code, then refining locally — the refine is load-bearing, because first-hit-wins
reported the confidence of a slightly-off read, which dragged sessions under
the AMBIGUOUS threshold and sent verified streamers to review.

**After: 20/20 codes, 60/60 frames at 720p, and the sweep runs faster than
before the fix.** Corpus unchanged (1080p 100%, 720p 100%, 480p 92%).
False-positive guarantee intact: zero absent finds, zero occluded, zero
too-small, replayed footage still verifies nothing. The previously flaky
pipeline gate is 12/0 three runs running.

`_gate-decoder-codes.mjs` now re-draws codes every run, so the next bad glyph
sequence fails CI instead of a payout.

## Stream context — a gate, not a dial

Shipped: no playback counts inside the first **10 minutes** of a broadcast
(`BOUNTY_STREAM_WARMUP_MS`, primary); the stream must continue at least **60s**
past the last counted playback (`BOUNTY_STREAM_TAIL_MS`, secondary). Both
pass/fail. Failures route to human review naming the specific condition.
**Payout is unweighted and unchanged.**

Deliberately absent, and asserted absent by the gate so it cannot return under
another name: no viewer-count threshold (absolute or relative), no
playback-spacing rule. The bounty amount is already a derivative of the
streamer's audience; gating on viewers charges twice and hits mid-size
streamers hardest.

**The bug this surfaced:** the first implementation asked the platform for the
broadcast start *at verify time*. Verification is VOD-first, so it runs after
the stream ended, when the channel reads offline and the start time no longer
exists. Every honest session would have routed to `NO_BROADCAST_START` review.
Broadcast start is now captured at clip playback while the channel is provably
live, and persisted. Second defect from the same seam: the capture lived only
in the room clip hook, so `/api/bounty/admin/playback` — the route the dress
rehearsal drives during a real broadcast — recorded nothing at all. The one
session that matters most would have carried no context data.

Routes to review: warmup violations, too-short tail, unknown broadcast start
(when credentials exist), below-floor quality. **"No platform API configured"
is `notEvaluated`, not a failed check** — routing every session to review when
credentials are absent floods the queue, and a flooded queue hides the farming
the check exists to catch.
