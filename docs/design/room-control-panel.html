What the audit found

Measured in the browser against the running dashboard, then traced into the server. The layout problems are the ones you can see; the dangerous ones are underneath.

CriticalA typo in “Max spend / viewer” takes the room’s join page down
It’s a free-text field. Nothing validates it on the way in — dashboard-routes.js checks only tokens and the payout address, and rooms-store.js does a bare String(). So "2 usd" persists happily, and then toAtomic throws inside roomAtomics, which /api/config calls unguarded. The room stops loading for every viewer.
CriticalChoosing “Points” rewards silently pays nobody, forever
Points force decimals: 0, but the default drop amount is 0.1. toAtomic('0.1', 0) truncates to 0, and the credit function returns early on any zero amount. No error, no warning, no log the streamer can see — the card keeps displaying “0.1 USDC per drop” exactly as it would if it were working.
HighThe most expensive setting in the product has no control at all
lazyConnectScope decides whether LiveKit connects per-seat or for the whole broadcast — the difference the handoff doc puts at roughly 7,200 LiveKit minutes a month. It exists in the store and the server reads it. There is not one reference to it anywhere in web/. The only way to set it is hand-editing rooms.json.
HighSaving one nested setting wipes its siblings
updateRoom shallow-merges config, so a patch containing just letters.enabled destroys every other letters field — they silently revert to defaults on the next read. Any partial edit has to send the complete nested object.
HighWhat you save is not what you get
Bounds are applied when the room is read, not when it’s written. Send maxSeconds: 60 and the server answers 200 OK — while the effective value is 30. The form has to reconcile against the response instead of trusting its own state, and today it doesn’t.
LayoutThirty controls, no hierarchy, five money fields that don’t say what they price
Everything past the first screen sits inside a single disclosure called “Advanced — fine-tuning” holding 20 of the 30 controls. Two different fields are both labelled “Room password.” Five numeric fields — Price per second, Flat price, Charge amount, Charge interval, Interval — are visually identical and belong to three different subsystems. And maxSeats, whose only legal values are 1, 2 and 3, is a text box.
HonestyControls that pretend to work
“Followers only” and “Subscribers only” render as live, clickable checkboxes. They are stored and completely inert — nothing reads them until platform verification ships. The reward token hint still says “Arc Testnet”; the chain has been Tempo for a while. Neither is a bug the streamer can see, which is the problem.

The proposed split

The page fails mostly because it asks a stranger to make thirty decisions before they have a room. Creating and running are different jobs, and only one of them is urgent.

Create — four decisions, one screen
  1. Name the roomFree text, 64 characters, with a counter — the server truncates silently today.
  2. Claim the linkmegachat.fun/yourname — 3–20 characters, with a live availability check. Needs a new endpoint; none exists, so the only way to learn a name is taken is to submit and read the 409.
  3. Free or paidA real fork, not a checkbox buried among others. Paid reveals exactly one field: the per-second rate.
  4. Create roomEverything else takes a sane default and moves to settings.

Everything below this line renders only while managing a room. That follows the rule already written in DESIGN.md — a card whose empty state says “do the thing you haven’t done yet” shouldn’t be mounted yet. Seven tabs, each one a coherent job, none of them longer than a screen.

Decide these before building

  • Who invents the bounds? Only three settings have real server limits — seats 1–3, clip length ≤30, watch gate ≤24h. Every price and interval is unbounded server-side. The numbers we put in the steppers are inventions, and they become the product’s de-facto rules.
  • Does the form fix the server, or work around it? Bounds are applied on read, so the UI can display a value the server will quietly override. Mirroring the clamps into the controls is the honest fix; validating on write in dashboard-routes.js is the real one.
  • Two names, one meaning. Pinned co-hosts count toward the MegaChat playback slot check but not the seat cap. A room with one seat and one pinned co-host takes paying joiners forever and never plays another clip. Any UI that explains seat capacity will be wrong until that’s reconciled.
  • Spam floor for bounty claims — your ask, now written up in OPEN-ISSUES.md with the insertion points. It needs one decision first: a pledge can name up to three streamers, so does the floor mean “clears the highest of them” or “rejects only the ones it misses”?
