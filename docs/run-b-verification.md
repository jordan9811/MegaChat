# Run B — real verification: how it works, what is proven, what remains

**Date:** 2026-07-28 · **Branch:** `feat/run-b-verification`

## The loop, end to end

1. **A clip plays** during an air session. The server opens a playback window
   and issues rotating codes bound to that playback (`bounty-watermark.js`).
   The overlay renders each code as **5×7 dot-matrix glyphs inside a white
   registration ring** (`public/code-matrix.cjs` — one font table shared by
   writer and reader, drift impossible). Concurrent **viewer count** is
   captured into the evidence chain at the same instant (Twitch Helix / Kick
   channels; unbackfillable).
2. **Verification samples timestamps** at code-validity midpoints
   (`bounty-verifier.js`), pulls frames from the **VOD** at those offsets
   (`frame-sources.js`: Helix archive discovery → extractor seam → ffmpeg
   grab; live HLS spot-check shares the path minus discovery), and decodes
   them with the **deterministic matrix reader** (`bounty-ocr.js`): locate the
   ring geometrically at any scale, sample the dot grid, match glyphs, measure
   `pixelHeight` — the anti-shrink number the verifier's floor enforces.
3. **Verified playbacks** flow to the release math (stubbed settlement),
   **ambiguous** results and **source-unavailable** states open review-queue
   items, and everything a payout is computed from lives in the append-only
   evidence chain.

| occluded (60%)  | 12     | 0     | 0%   | —               | —                 |
| absent          | 12     | **0 false positives** | 0% | — | —              |

**Minimum verifiable stream quality: 720p.** At 480p the glyphs land at
12.3px — right at the verifier's 12px legibility floor — and detection drops
to 92% with marginal confidence. 480p-only streamers can be verified but
should expect occasional AMBIGUOUS results routed to review; below 480p the
mechanic cannot verify and says so rather than failing silently. Corpus is
regenerated by `node _corpus-run-b.mjs` (never checked in); rates by
`node _gate-run-b-ocr.mjs`.

## Proven tonight (no live broadcast needed)

- The **entire distance over HTTP** (`_gate-run-b-pipeline.mjs`, 12/0): real
  issued code → real overlay pixels → 720p/3Mbps re-encode → real decoder →
  `PASS` at confidence 0.83 → release computed from it (stub).
- **Replay defense**: frames carrying a different session's code verify zero
  and pay nothing.
- **Failure honesty**: deleted/sub-only/unprocessed VOD, offline channel, or
  a missing extractor produce typed `SOURCE_UNAVAILABLE`, land in the review
  queue, and pay nothing while unresolved — never a FAIL.
- **Stingers undisturbed** after the badge change (real-page suites all green).

## Pending exactly one real broadcast

Live HLS grab and VOD discovery against a real channel, end to end. The
one-command harness:

```bash
node _rehearsal-run-b.mjs --handle <twitch-login>
```

With `TWITCH_STREAM_KEY` set it broadcasts unattended (overlay screencast over
a test pattern via RTMP, ~12 min — set a test title on the channel first);
already live with the overlay in OBS, pass `--skip-push`. It opens a real air
session, drives three real playbacks, live-spot-checks mid-broadcast, polls
for the VOD, runs the primary verification, and prints verdicts + release
rows + where the viewer samples landed.

## Timestamp tolerance

±1.5s, derived: sampling happens at code-validity midpoints and the shortest
window (code clamped to a 3s clip end) leaves ≥1.5s of on-screen code either
side; ffmpeg's pre-input seek is accurate well inside that.

## Kick

Identity claim (OAuth 2.1 + PKCE, slug-based), app-token live status and
viewer capture all real. **VOD discovery does not exist in Kick's official
public API** — VOD pages extract fine by direct URL, but timestamp→VOD lookup
needs the unofficial Cloudflare-guarded v2 web API. Kick verification is
live-first; operator-supplied VOD URLs work. Platform finding, filed.

## Where I would attack it (design pushback)

1. **Play the clips to nobody.** The verifier proves clips AIRED, not that
   anyone watched. Stream at 4 a.m. to zero viewers, play everything, collect.
   Viewer samples are already in evidence — the payout formula should weight
   by them (that was the point of capturing them), but nothing enforces it
   yet. **This is the weakest joint.**
2. **Point the overlay at a private "broadcast".** Push the overlay to the
   claimed channel, but make the actual content a static image with clips
   "playing" server-side while the stream shows nothing else. Codes air,
   verification passes. Defense: moderation + streamer approval don't help
   (it's the streamer doing it); viewer-weighting again is the answer — a
   nothing-stream has no audience.
3. **480p on purpose.** Stream at the marginal quality so most samples read
   AMBIGUOUS and land with a human who might wave them through. The review
   queue's SLA pressure is the exposure; reviewers need the detection-rate
   table (this doc) as context.
4. Re-streaming someone else's broadcast with the overlay composited on top —
   codes air over stolen content. Moderation of the CLIPS doesn't see the
   surrounding stream. Platform ToS enforcement is the realistic backstop; we
   cannot verify surrounding-content ownership from frames alone.

The defense holds where money is computed from evidence (codes, sizes,
replay, source honesty). It does not yet hold where the mechanic meets
economics: **verified airtime with zero audience still pays**. Viewer-weighted
release is designed for, captured for, and should be the next money change.
